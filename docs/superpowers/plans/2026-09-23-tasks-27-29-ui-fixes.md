# Tasks 27-29: three phone UI defects (loot list, village stopwatch, market filters)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix the three small UI defects the owner reported from a phone playtest (`docs/TASK_BOARD.md` §27, §28, §29): the loot list's top row is cut off, the Village stopwatch spins as a whole, and the Market filter checkboxes are misaligned. Each fix also gets a guard, so the same shape cannot come back unnoticed.

**Architecture:** The three have different causes, and one of those causes is shared and is NOT in the component code:

- **27 is a real CSS defect in current `main`.** It is a flexbox shrink rule. Because the rows are sorted by rarity and only rare rows are affected, it always hits the top rows. Chromium reproduces it on desktop, so Playwright can prove both the defect and the fix.
- **28 and 29 are very probably already fixed in `main`, and the phone never received the fixes.** The over-the-air bundle version is stamped only once, when the stack is first brought up (`ops/oracle/README.md` "Bring it up", ~lines 199-206). The `deploy` skill's "every deploy" command (`.claude/skills/deploy/SKILL.md`, "Ship") never re-stamps it. So the live manifest has answered `1.0.464` since the first stamped deploy, and `git rev-list --count 5c97b53` = **464** (2026-09-12 01:36 +0200). Every later deploy rebuilt a zip under the same name, `1.0.464.zip`. A phone that already holds `1.0.464` compares equal and never downloads again. Caddy also serves `/updates/*` as `Cache-Control: public, max-age=31536000, immutable` (`ops/oracle/caddy/Caddyfile` ~131-136), even though the deploy overwrites the file behind that name. The stopwatch fix `4926886` is commit **#479** and the checkbox fix `9474630` is commit **#520**, so neither reached the phone. `main` is at **#647**. The two symptoms match that era's code exactly: `.stopwatch svg` rotated whole, and `.filters input` stretched each checkbox to 272-288px.
- So for 28 and 29 the plan is: (a) make the bundle version move on every deploy, and make the app say which bundle it is running; (b) still harden both components, so the fix does not depend on `transform-box` or on a 44px native checkbox; (c) verify on the phone after one correctly stamped deploy.

**Tech stack:** Svelte 5 (runes) + Vite in `client_web`, the Capacitor Android shell with `@capgo/capacitor-updater`, Playwright geometry scripts in `client_web/scripts`, and vitest in `client_web/tests` (`environment: 'node'`, so tests read source files; they do not render components).

#### Diagnosis, with evidence

1. **The code in `main` already rotates only the hands.** In `Village.svelte`, the crown/bow `<path>` (line 113) and the hand `<path class="hand">` (line 114, and again at 157) are separate elements. The CSS at 287-291 animates `.stopwatch .hand` with `transform-box: view-box; transform-origin: 12px 13px`. Nothing animates the `<svg>` any more.
2. **"The whole icon spins" is the pre-`4926886` rule**, `.stopwatch svg { animation: tick ...; transform-origin: 50% 54% }` (see `git show 4926886 -- client_web/src/routes/Village.svelte`). Suppose the WebView ignored `transform-box` under the current code. The hand would still be the only thing that moves: it would swing about the wrong pivot, and the case and crown would stay still. So a phone that shows the whole watch spinning is running a bundle from before `4926886`. The symptom itself identifies the bundle.
3. **Why the phone is on an old bundle.**
   - `ops/oracle/README.md` ~202-205 stamps `FOLKIDLE_BUNDLE_VERSION="1.0.$(git rev-list --count HEAD)"` into `.env` once, at "Bring it up".
   - The `deploy` skill's every-deploy command is only `git push ...` plus `docker compose up -d --build`, and it never re-stamps.
   - The task board records the live manifest as `1.0.464.zip`, with `main` at 647 commits.
   - `web.Dockerfile` ~59-61 zips the current `dist` under whatever name `.env` says. The name therefore stayed `1.0.464` while its content changed underneath it.
   - `capacitor.config.json` has `autoUpdate: "onLaunch"`. The plugin applies a bundle only when the manifest's version differs from the one it holds.
   - If the phone never updated at all, it runs the APK's built-in bundle (built 2026-09-12 00:04). That is also before `4926886`.
4. **The app cannot tell anyone which bundle it runs.**
   - `liveUpdate.ts:84-97` exports `runningBundleVersion()`, documented "for the Settings screen". **Nothing reads it**: `grep -rn runningBundleVersion src` matches only its own definition. This is the "grep for a WRITER as well as a reader" trap in reverse.
   - Settings → About (`Settings.svelte:704-707`) does show `APP_VERSION` and `build {BUILD_ID}`. `BUILD_ID` is the UTC build timestamp compiled into the bundle, so it already tells the bundles apart.
   - `APP_VERSION` is `package.json`'s `1.4.0`, which is the same for every bundle, so it does not.

  ```svelte
  <script lang="ts">
    // Modul: ONE STOPWATCH, drawn once. Village drew the same SVG twice at two
    // sizes, and task 28 had to be fixed in both.
    //
    // THE HANDS ARE DRAWN AROUND (0,0) INSIDE translate(12 13), so the dial
    // centre IS the hand's own origin. A plain rotate() then turns about the
    // centre with no help from transform-box - which 4926886 relied on, and
    // which the owner's phone was suspected of ignoring. It was actually on a
    // stale bundle (see Village's task-28 note), but the pivot should not
    // depend on an engine resolving `transform-origin: 12px 13px` against the
    // right box. `transform-origin: 0 0` is the one value that means the same
    // thing under view-box and under the initial value; only fill-box would
    // move it, and view-box is set explicitly below.
    interface Props {
      /** Rendered size in px; the viewBox is always 24. */
      size?: number;
      /** Accessible name. Omit for a decorative watch next to text that already says it. */
      label?: string;
    }
    const { size = 14, label }: Props = $props();
  </script>

  <span
    class="stopwatch"
    role={label ? 'img' : undefined}
    aria-label={label}
    aria-hidden={label ? undefined : 'true'}
  >
    <svg viewBox="0 0 24 24" width={size} height={size} fill="none" stroke="currentColor"
         stroke-width="2" stroke-linecap="round">
      <circle cx="12" cy="13" r="8" />
      <!-- The crown and the bow, which do not move. -->
      <path d="M9 2h6M12 2v3" />
      <!-- The hands, drawn about the dial centre. Was M12 9v4l2.5 2.5. -->
      <g transform="translate(12 13)">
        <path class="hand" d="M0 -4V0l2.5 2.5" />
      </g>
    </svg>
  </span>

  <style>
    .stopwatch {
      display: inline-flex;
      align-items: center;
      color: var(--accent);
      flex: none;
    }

    /* A stopwatch that does not move is a picture of a stopwatch. Only the
       hands turn; the translate on the parent <g> is an SVG attribute, not
       CSS, so this animation's transform cannot overwrite it. */
    .hand {
      transform-box: view-box;
      transform-origin: 0 0;
      animation: tick 2s steps(8, end) infinite;
    }

    @keyframes tick {
      to {
        transform: rotate(360deg);
      }
    }

    @media (prefers-reduced-motion: reduce) {
      .hand {
        animation: none;
      }
    }
  </style>
  ```

  Important: the animation goes on the **inner path**, never on the `<g>`. A CSS `transform` on the `<g>` would *replace* its `transform="translate(12 13)"` attribute, and the hands would jump to the corner.

#### Diagnosis, with evidence

I ruled each suspect in or out from the code:

- **Sticky header: no.** Nothing in `SessionLoot.svelte` or its hosts (`Combat.svelte:458-460`, `Gathering.svelte:313`) is `position: sticky`. `.head` (196-201) is a plain flex row *outside* the `<ul>`.
- **The list's own padding or border: no.** The `ul` (208-243) has `padding: 0` and no border.
- **Transitions, `animate:`/`flip`, or `in:` on rows: none.** The `{#each}` at 130 has a key and no directives.
- **Scroll anchoring: already neutralised.** `overflow-anchor: none` sits on the `ul` at 242.
- **VirtualList rowHeight: not involved.** This list is not virtualised, and aggregation bounds the row count (`game.ts:175-180`).
- **The cause is flex shrink on the rare rows.**
  - The `ul` is `display: flex; flex-direction: column` with `max-height: 16rem; overflow-y: auto` (211-219).
  - Every `li` is a flex item with the default `flex-shrink: 1`.
  - An item normally cannot shrink below its content, because its automatic minimum size is `min-height: auto`. **But the automatic minimum applies only to items that are not scroll containers** (CSS Flexbox §4.5). Rows with `shouldGlow(tier)` (tier ≥ 10, `rarity.ts:67-69`) get `class:folk-sweep` (line 132), and `app.css:995-998` sets `.folk-sweep { position: relative; overflow: hidden; }`. That makes those rows scroll containers, so their minimum height resolves to **0**.
  - Once the list has more rows than 16rem holds (about ten rows of ~24px), the column's negative free space is taken **entirely from the rare rows**. They are the only items allowed to shrink, and they shrink until only their padding and border are left (~4px).
  - Rows are sorted by rarity descending (`aggregate`, 81-83), so the rare rows are **always the top rows**. That gives the report exactly: "with many items ... the top item is cut off".
  - A short list never overflows, so nothing shrinks, which is why it looks fine early in a session. "Glitches" fits too: every inserted row changes the overflow and re-sizes the squashed rows.
  - The Materials list is unaffected because its rows never get `folk-sweep`.
  - The "Ancient pendant sliced in half at the top edge" in the `overflow-anchor` comment (lines 230-231) was an Ancient (tier ≥ 10) row. It may well have been this same shrink, not only anchoring.
- **Why no checker saw it.**
  - `clipping-check.mjs` states "Vertical overflow is NOT checked" (line 25). Its collapsed-element test (165-184) is width-only.
  - The session loot log is client-side memory, filled only by live `onLootDrop` packets (`game.ts:825-845`). A checker that navigates straight to Combat renders "Nothing yet."
  - `check:touch` and `check:overlap` only look at controls, and a loot row has none.

#### How to approach this (for the implementing agent)

Reproduce first, fix second, guard third. The defect is ordinary flexbox behaviour, so desktop Chromium in Playwright reproduces it exactly: no phone is needed for 27. The one-line fix is `flex: none` on the row. Do **not** remove `overflow: hidden` from `.folk-sweep`: the sweep and the burst sparks deliberately overshoot the row and must be clipped, and four other callers rely on it (`VictoryCard`, `Combat:323`, `Forge:473/657`). Make the checker able to see the defect before you fix it, and confirm it goes red on the unfixed code. A guard that has never failed has not been shown to work.

#### Diagnosis, with evidence

- **The task board's premise is out of date.** It says "the CSS does not lay the labels out as a grid". In fact `.checks` has been a grid since `5c97b53` (2026-09-12 01:36): `display: grid; grid-template-columns: repeat(auto-fill, minmax(10.5rem, 1fr))` at `Market.svelte:788-804`, with `.filters .checks { flex: 1 1 100% }` at 623-625 giving it a full row.
- **The reported symptom matches the pre-`9474630` defect.** That commit (2026-09-17, #520) fixed `.filters input` → `.filters > input` (591-609). The unscoped selector had given every nested checkbox `flex: 1 1 12rem`, which stretched each one to 272-288px, a different width per row. The reporter then said "each checkbox is positioned slightly differently", which is what "misaligned" describes now. A phone frozen on `1.0.464` (commit #464) has the grid but **not** this fix (see task 28). So the owner most likely saw old code.
- **What is still wrong in `main` at 390px:**
  - Panel content is ~328px (390 − 2×0.6rem grid padding − 2×0.7rem panel padding − fieldset padding/border).
  - `minmax(10.5rem = 168px)` + 9.6px gap needs 345.6px for two tracks, so a phone gets **one column**: 11 type rows plus 5 tier rows, each 44px tall, about 700px of checkboxes.
  - The track is that wide only because the checkbox itself is the 44px target. `app.css:1188-1197` forces `input[type='checkbox']:not(.touch-exempt)` to 44×44 with `flex: 0 0 44px`, so each cell is 44px + gap + "Scorched Wasteland" on one line (`white-space: nowrap`, 818).
  - `.checks label` has no `min-height` of its own and no equal-cell rule, so its height comes from whatever the checkbox is: 44 on a phone, ~13-16 on desktop.
  - That is "tidy" only at one width, and it wastes a phone screen.
- **How the rules interact:**
  - `.filters > input` (606-609) reaches only the search field, a direct child. Checkboxes are `fieldset > label > input`. **Keep the `>`.** Its comment explains exactly what broke without it.
  - `.panel *:not(img):not(svg):not(canvas):not(button):not([role='button']) { min-width: 0 !important }` (`app.css:443-445`) reaches the label and the checkbox. The checkbox must hold its size by `flex: none`, not by `min-width`.
  - The app.css checkbox floor is `(0,2,1)` via `:not(.touch-exempt)`. A scoped `.checks input.svelte-xyz` is also `(0,2,1)` and comes earlier in the cascade (component CSS is injected before or after app.css depending on the build), so do **not** try to out-specify it. Opt the checkbox out by name with `class="touch-exempt"`, which is the escape hatch app.css provides (1098-1101).
  - A checkbox cannot be enlarged by padding (hit-testing uses its border box, `app.css:1178-1183`), but a `<label>` wrapping it *is* a hit target for it: a tap anywhere on the label toggles the box natively.
  - `check:touch` currently measures only `input` (`touch-check.mjs`, the `controls` query), so a small box inside a 44px label would be reported as undersized unless the script credits the label. That change is legitimate: it measures what the thumb actually hits.
