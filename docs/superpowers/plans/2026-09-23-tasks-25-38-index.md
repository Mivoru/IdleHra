## Findings from planning that change the order (2026-09-23)

The planning pass found three things that are more urgent than anything on
the board:

- **A. Phones have not received a web update since 2026-09-12.** The
  over-the-air bundle version is stamped once, at stack setup, and never again
  (see the plan for 27-29). The manifest has said `1.0.464` for 180 commits,
  and Caddy serves `/updates/*` as `immutable`, so the APK never downloads a
  newer bundle. That alone explains 28 and probably 29, and it means **no
  client fix can be checked on the phone until the deploy re-stamps the
  version.** Do this first. It is small: re-stamp on every deploy, add a
  post-deploy manifest check to the `deploy` skill, and show the running
  bundle in Settings → About.
- **B. Live Guild War code pays diamonds with no cap, and it can be farmed**
  (the task 38 audit, "Phase 0"). A win pays 100 diamonds to every member,
  more than the Delve's whole weekly ceiling, and pairing re-settles on every
  new pair, so alt guilds can create and disband to force repeated payouts.
  Nobody has done it yet, because only one guild exists. **Owner decision
  2026-09-23:** Guild Wars unlock only at 50 qualifying players (see the 38
  plan's "OWNER DECISION"), so Phase 0 is the population lock. It also closes
  the exploit. It should ship right after A. The rest of 38 waits until the
  population nears the floor.
- **C. This machine's `.claude` hooks have probably been skipping their
  checks.** DaVinci Resolve set a user-level `PYTHONHOME`, and every hook
  fails open (see 35). Remove that variable before any content edit (33).

Also found, not urgent: the Rarity skill node does not do what its text says
(26, H4), the area-completion luck bonus is unreachable (26, H5), the economy
audit throttles combat gold to 75% because it cannot see most sinks (37),
`ExecuteAttackAsync` opens its transaction outside its `try` (25/36), and
`CronWorkerGuardTests` scans only `Engine/` (30).

## What may run at the same time on this machine

- **Only one `dotnet test` at a time.** `SustainedLoadTests` binds port 8095
  and the Testcontainers fixtures share Docker. Two agents running the suite
  will fail each other in ways that look like code errors.
- **Only one `npm run exercise` at a time, and re-seed between runs**
  (`--seed-dev`). It spends fixture state and signs in as the dev fixture. A
  second browser signed in as the fixture disables every Fight button (see the
  memory note on the exercise session conflict).
- **Stop the server before `dotnet build`.** The `guard_stale_build.py` hook
  blocks the build while the server runs, and a blocked chained command runs
  *nothing*, including any edit chained in front of it.
- Parallel implementation is therefore safe as **one server-side agent plus
  one client-only agent**, each in its own worktree (`isolation: "worktree"`),
  with only one of them running the suite or `exercise` at any moment. Planning
  and reading can be parallel without limit.

## How an agent should approach each kind of task

### A defect players see (25, 27, 28, 29)
1. **Reproduce before reading further.** Use the `run-stack` skill, get the
   failure on screen, and for 25 force the event window open (a window's
   calendar dates are not a repro).
2. **Find the first broken link, not the most suspicious line.** The
   `wiring-auditor` agent exists for server features that "should work". This
   codebase's dominant defect is an output side that was never wired, plus
   silent rollbacks, so ask what the player *sees* on each refusal path.
3. **Write the failing test first**, and have it do what a real client does
   (send the real command against the fixture's real state), not what the
   engine test already covers. `WorldBossArmourTests` passing while nobody
   could attack is exactly this gap.
4. Fix it, then run the `verify` skill in its own order: unit tests, the suite,
   `exercise`, and for UI the geometry checks at 390px.
5. **Add the regression guard where the class lives**: an `exercise.mjs` step
   for gameplay, a fixture that renders enough rows for a checker, a vitest for
   markup. One case of a bug usually means a class of it.
6. Deploy with the `deploy` skill (standing approval), then check on production
   or on the phone. A CSS fix for Android WebView is not verified until it has
   been seen on the phone.

### An investigation (26)
Measure before changing anything. Print **and assert** every term (CLAUDE.md:
"a number a test PRINTS is not a number a test CHECKS"). Separate "defect" (a
luck term missing or zeroed, which you fix) from "design" (the weights, which
the owner decides). Leave behind the instrument that would have answered the
question, which here is the drop record.

### A deletion (33, 34)
First list every reader, then prove the list is complete (a repo-wide grep and
production SELECTs). Then add a guard that would fail if a reader were missed,
and only after that delete. Keep each step revertible and in its own commit.
Irreversible or production-facing steps get an explicit owner go-ahead, even
under standing approvals.

### Hygiene (30, 31, 32, 35)
Low risk, but "delete a branch" and "bump a CI action" are outward-facing. List
what is not provably merged for the owner rather than deleting it. Watch the CI
run go green; a pushed workflow counts as done only once CI has actually run it.

### A design (36, 37, 38)
Do **not** write code first. Take the brief's options to the owner as a short
list of real choices with trade-offs, get decisions, and write a spec to
`docs/superpowers/specs/`. Then turn the spec into a phased plan whose first
phase is the smallest playable slice, and build behind a flag. Every design
has to respect the ledgers the repo already enforces: `PowerCeilingTests` (no
uncapped linear lever), `DelveRegistry.MaxDiamondsPerWeek` (the calibrated
diamond tap), the two gold paths, and "the client sends a choice or a measured
outcome, never a number the server trusts".
