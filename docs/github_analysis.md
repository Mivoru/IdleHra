# FolkIdle Repository Analysis Report

## 1. Architectural & Structural Flaws

- `server/FolkIdle.Server/Domain/Combat/SimulationEngine.cs` remains a large orchestration boundary. Its constructor and state surface span combat, progression, gathering, crafting, village, guilds, breeding, market, world-boss activity, persistence, anti-cheat telemetry, and notification queues. This violates separation of concerns and makes it difficult to prove that a state field is handled consistently by live simulation, offline simulation, login hydration, checkpointing, and logout.
- The server uses a mutable `TickStatePayload` plus approximately 35 cross-thread queues in `PlayerSessionRegistry`. The single-thread tick model avoids locks, but ownership is implicit: a producer can enqueue a result that has no durable retry, no idempotency key, or no guaranteed consumer during shutdown.
- Durable state is split across live payload fields, Redis frames, database checkpoints, REST query caches, and WebSocket snapshots/events. `StateCheckpointManager` has improved boundary handling, but every new field still requires independent decisions about hydration, frame inclusion, checkpoint persistence, dirty-state tracking, and client projection. This is a recurring source of fields that are read but never written or written but never loaded.
- The live Svelte client and retired Unity client contain parallel packet structs, caches, command dispatchers, and WebSocket implementations. `client/` is not the production client, but its code remains sufficiently complete to invite edits to the wrong implementation and to preserve obsolete protocol assumptions.
- The client has two consistency models: authoritative WebSocket state/events and REST/query-cache data. Command results trigger invalidation asynchronously, so screens such as Mailbox, Character, Larder, and Market can display a stale response or apply a later REST result over a newer WebSocket update.
- Protocol generation and layout guards reduce wire drift, but the fixed-layout/index-based protocol still makes ordering an API. Affix stop conditions and packet fields are vulnerable to semantic drift unless every ordered registry is checked element-by-element.
- The codebase relies on runtime browser checks for several classes of correctness that `svelte-check` cannot detect: Svelte 5 snippet invocation, `$derived` shadowing, legacy `export let`, dynamic native selects, hidden `<details>` content, and stacking contexts. The static type-check result is therefore not an adequate release gate.
- Raw SQL and EF naming have a high operational coupling. PascalCase default tables and selected snake_case overrides are easy to confuse, and relation-name errors are runtime-only.
- Error handling is inconsistent. Some command handlers now return explicit result codes, but other paths still roll back and leave the player with no visible explanation. This turns a valid server-side refusal or transient error into an apparent dead button.

## 2. Security Audit & Exploit Vectors

- **MEDIUM — bearer DeviceId authentication.** `server/FolkIdle.Server/Models/PlayerRecord.cs:9-33` and `server/FolkIdle.Server/Engine/AuthenticationEngine.cs:666-700` treat a client-persisted DeviceId as sufficient for remembered login. A stolen, cloned, or extracted device identifier can authenticate without the password. Replace it with a server-issued, revocable device credential and require reauthentication for sensitive actions.
- **MEDIUM — JWT revocation gap.** `server/FolkIdle.Server/Engine/AuthenticationEngine.cs:80-179` and the logout path in `server/FolkIdle.Server/Network/NetworkBroadcastSystem.cs:8071-8195` leave a valid JWT usable until its 24-hour expiry. Refresh-token rotation and theft revocation are sound, but a stolen access token cannot be invalidated on logout or password reset. Use short-lived access tokens with a server-side session/revocation check or rotate an access-token family.
- **LOW — deployment secret/session consistency risk.** JWT signing material and Redis/session state must be identical across instances. A secret mismatch or inconsistent session store can break revocation semantics and create operational authentication failures. Add startup parity checks, managed secret rotation, and a tested multi-instance deployment configuration.
- The server-authoritative model is substantially stronger than trusting client state: commands are interpreted server-side, epochs are used for session ordering, market operations use serializable transactions and row locks, and purchase ledgers provide idempotency. These controls reduce direct packet-spoofing and duplicated-purchase risk.
- Refresh tokens are hashed, rotated, and replay detection revokes the token family. Password hashing uses PBKDF2-HMAC-SHA256 with fixed-time comparison. These are appropriate primitives, but their protection depends on secure token storage in the browser/device and TLS termination being correctly configured.
- WebSocket authenticity is session-based rather than message-signature-based. A valid authenticated socket can issue commands, so authorization must remain server-side for every opcode, character, item, market row, and account scope. Any future command that accepts a client-derived amount, probability, timestamp, inventory state, or registry index must be rejected unless independently recomputed.
- Replay resistance is stronger for refresh tokens and epoch-gated commands than for every possible application message. Audit all command handlers for idempotency keys or monotonic request identifiers; reconnect/retry must not duplicate a spend, reward, trade, breeding action, or purchase.
- Local time changes should not grant progress if elapsed time is derived only from trusted server timestamps and persisted logout/checkpoint state. Offline simulation still has a high-value trust boundary: validate timestamp monotonicity, cap elapsed time, handle clock rollback explicitly, and record suspicious deltas. A client-controlled last-seen timestamp would enable catch-up inflation.
- Unity memory editing is not preventable on the client. It is acceptable only because currency, inventory, cooldowns, combat outcomes, and offline rewards are server-authoritative. Never expose a client value as proof of entitlement, and treat client anti-cheat telemetry as a signal rather than an authority.
- Review logs, crash reports, browser storage, and diagnostic flight recorders for JWTs, refresh tokens, device identifiers, email addresses, and purchase tokens. Client-side storage remains readable by an attacker with device or browser access.
- Receipt verification must remain store-backed and fail closed. The legacy signature envelope described in `CURRENT_IMPLEMENTATION_STATE.md` is not a real Google/Apple purchase format and must not become an accepted production fallback when store credentials are absent.
- No hardcoded production credential was identified in the reviewed architecture; the documented development fixture credential and environment-based deployment secrets must remain excluded from production bundles, logs, and committed configuration.

## 3. Game Logic & Math Discrepancies

- Core progression is geometric (`250 * 1.16^level` XP and approximately `100,000 * 1.092^(level-1)` base HP), while power also multiplies lineage, attributes, inheritance, skills, aptitudes, equipment, affixes, sets, potions, mastery, codex, guild, and global bonuses. The multiplicative surface is still large enough that local caps can be defeated by adding another uncapped lever.
- Codex yield was measured at 71.9x and is now capped, but codex damage is documented at approximately 142x and remains intentionally open. This is a high-risk pacing and economy lever: it shortens fights, increases kill/loot/gold throughput, and compounds every other reward multiplier.
- Existing `PowerCeilingTests`, `GatheringEconomyTests`, and `MonsterLadderTests` are useful guards, but several accepted ranges are broad. They constrain authored snapshots and current sinks, not lifetime stockpile growth after finite crafting, village, and upgrade sinks are exhausted.
- Offline combat is an expected-value projection in `OfflineSimulationEngine.cs`, while live combat is discrete: hit/miss, crit, food thresholds, death, first-clear modifiers, and equipment drops. The approximation can diverge materially near one-hit death, low hit chance, short encounters, boss thresholds, and food depletion. There is no general stochastic error budget or reconciliation test across representative builds.
- Offline catch-up is capped at 12 hours, but repeated short logins can collect approximately 24 simulated hours per real day. This makes progression dependent on login cadence and creates a potentially unintended optimization over remaining offline longer.
- Offline actions and loot are converted from continuous estimates to integer counts, then clamped (`MaxOfflineKillsPerSlot`, `MaxOfflineLootRolls`, integer summaries). Truncation creates threshold discontinuities, while saturated summary counters can stop representing actual grants.
- Village passive production clamps to warehouse capacity. This prevents unbounded storage growth but silently discards production when full and is not clearly represented in the offline summary. It can look like a broken building or create a softlock when a required resource cannot be collected because the storage condition is not visible.
- The two gold paths are correct only if every producer is classified correctly: some earnings update `CurrentGold` plus `RedisPendingGoldDelta`, while database-crediting paths update `CurrentGold` only. The documented Village upgrade and feast paths still debit the database commodity row without updating the live session, leaving stale affordability/UI state until relogin. This boundary is vulnerable to future double-payments or stale balances.
- `OfflineSimulationEngine.GrantVillagePassiveProductionAsync` catches and rolls back database errors without logging or retrying. Offline production can therefore disappear while login succeeds and the payload is marked dirty. This is a current durability defect, not merely a balance concern.
- Loot worker failures are isolated so the worker survives, but failed requests are logged/discarded. A transient database or pooler failure can permanently lose a reward unless an idempotent durable retry/outbox exists.
- Persistent checkpoint failure leaves dirty state for later retry. Without per-player backoff, a long database outage can create repeated checkpoint pressure and worsen the outage.
- No unbounded primary production loop was found after the budgeted gathering drain fix, but budgeted queues can still grow without limit when producers exceed database throughput. This is an eventual backlog failure rather than an in-call infinite loop.
- Historical defects documented as fixed include geometric monster damage against linear player HP, flat armour scaling, zero canonical dodge, divergent offline attribute growth, impossible breeding gates, unreachable villager capacity, and silent combat/breeding rollbacks. They should be treated as regression-sensitive boundaries, not evidence that the underlying architecture is simple.

## 4. Performance Bottlenecks

- `SimulationEngine` runs at 10 Hz and parses/produces a broad snapshot path. The browser client receives JSON snapshots and dispatches them through Svelte stores; mobile WebViews and CPU-throttled devices can incur measurable main-thread parsing and reactive-update cost.
- Server database work is off the tick thread, but many paths use serializable transactions, row locks, and per-request persistence. Under Supabase pooler limits this can produce connection pressure, queue growth, retry amplification, and delayed rewards even while the tick remains responsive.
- `CombatLootEngine` now bounds gathering drains and isolates worker exceptions, preventing starvation and task death. It does not guarantee eventual drain or durable replay, so sustained production overload trades latency and reward loss for process survival.
- Offline return can produce large bursts, with up to 200,000 projected kills/loot rolls per slot before safety clamps. The resulting grouped work can pressure queues, database connections, allocations, and client event delivery.
- Browser state intentionally retains up to 25,000 equipment entries, 5,000 material entries, and 200 chat entries. These caps prevent an unbounded leak, but the retained object graph and derived aggregation can consume several megabytes in a long-lived mobile tab.
- REST inventory responses are now split/windowed and `VirtualList` prevents the historical 17,836-item DOM explosion. Call sites that invalidate only one of the equipment/material query keys can still leave stale screens, and an incorrect row-height contract can cause overlap rather than merely a visual inefficiency.
- The retired Unity client contains bounded receive queues and pooling patterns, but it is not the live runtime. Any future maintenance effort spent optimizing it without deleting or clearly archiving it increases cost without improving production performance.
- `SimulationEngine` shutdown drainage is time-bounded at approximately 1.5 seconds. Slow database operations or many active players can leave writes unfinished during deployment/restart unless every path uses the full graceful-drain route.
- Static event/query caches and per-session queues need memory telemetry. Queue depth heartbeats are useful, but production alarms should cover age of oldest item, retry count, dropped reward count, checkpoint age, and per-account payload size.

## 5. Missing Components & Blind Spots

- A durable outbox/retry/reconciliation mechanism for loot, gathering, offline production, and other reward grants is missing or not evident. Logging a failed grant is not equivalent to preserving it.
- A complete access-token revocation/session registry is missing; logout and password reset do not invalidate already-issued JWTs.
- A formal server-issued device credential lifecycle is missing. The current remembered-login DeviceId is a bearer identifier without proof of possession, rotation, or selective revocation.
- There is no demonstrated sustained-load scenario combining active combat, gathering, offline logins, checkpoints, market contention, reconnects, and Supabase-like pool limits. Unit and structural tests cannot expose queue-age and pool starvation interactions.
- Offline simulation lacks a quantified accuracy contract against live combat. The repository needs representative-build differential tests, explicit acceptable error bounds, and special cases for death, food, bosses, low hit chance, and short durations.
- Economy analysis does not appear to model the post-completion state where finite sinks are exhausted and production continues. A lifetime stockpile/inflation model and telemetry-based circuit breakers are needed.
- Fault injection coverage is incomplete for process crash during checkpoint, database failure during offline grant, shutdown timeout, Redis loss, reconnect races, and split-brain compensation failure.
- Client/server schema coverage is stronger than before, but no single state ownership manifest appears to define every field's source of truth, hydration path, persistence path, event semantics, and invalidation keys.
- Production observability needs explicit metrics for dropped rewards, stale live balances, queue age/depth, checkpoint retry rate, offline grant failures, suspicious clock deltas, token replay, and authentication/device-login anomalies.
- The repository retains a full Unity project despite the web client being the production client. It lacks a hard architectural boundary or archival policy preventing accidental protocol and gameplay edits in the retired client.
- Native-device verification remains incomplete for mobile-specific security and UX paths, including Android back-button behavior, native picker behavior, safe-area handling, and Capacitor plugin installation/runtime permission behavior.

## 6. Actionable Fixes

- **P0:** Replace DeviceId bearer login with a server-issued, hashed, revocable device credential bound to an account and device registration; require password or step-up authentication for sensitive operations.
- **P0:** Shorten access-token lifetime and add server-side session/revocation checks, including invalidation on logout, password reset, account purge, and confirmed refresh-token theft.
- **P0:** Make offline village production fail explicitly: log structured context, preserve the grant in an idempotent durable outbox, retry with bounded backoff, and surface a truthful login summary.
- **P0:** Introduce idempotent durable reward grants for loot, gathering, and offline equipment so worker/database failures cannot silently discard player progress.
- **P0:** Audit every command handler for server-side recomputation, authorization scope, replay/idempotency behavior, epoch validation, and explicit client-visible refusal results.
- **P1:** Split `SimulationEngine` into bounded domain coordinators with explicit state ownership and adapters for tick mutation, persistence, and notifications. Keep the single-writer tick invariant but reduce constructor and field coupling.
- **P1:** Define a machine-readable state ownership manifest covering payload, Redis frame, database checkpoint, login hydration, WebSocket packet, REST cache, and invalidation keys; make tests fail when a field lacks a declared path.
- **P1:** Add per-player checkpoint backoff, retry budgets, oldest-dirty-state metrics, and a recovery/reconciliation job for writes abandoned by shutdown or persistent database failure.
- **P1:** Add differential offline/live combat tests with documented error bounds and deterministic edge cases for food, death, bosses, low hit chance, short fights, and elapsed-time caps.
- **P1:** Close or deliberately curve every multiplicative progression lever, including codex damage, and add a lifetime economy simulation that measures stockpiles after all finite sinks are completed.
- **P1:** Keep gold accounting in one typed service with explicit debit/credit categories; update live session state for Village and feast debits and add invariants that reject double application of pending deltas.
- **P1:** Add sustained-load and chaos tests that combine active sessions, gathering, combat loot, offline catch-up, serializable market work, pool exhaustion, Redis loss, reconnects, and shutdown.
- **P2:** Add queue age, retry, drop, reward-reconciliation, and per-session memory metrics with alerts; cap or shed non-authoritative client history before mobile memory pressure becomes a crash.
- **P2:** Replace observed client health maxima with an authoritative server-provided maximum and define snapshot/event ordering guarantees for REST/WebSocket reconciliation.
- **P2:** Make all user-visible storage-cap and offline truncation effects explicit in summaries, including discarded production, clamped action counts, and saturated counters.
- **P2:** Add a repository boundary for the retired Unity client: archive or mark it non-buildable for production, document the sole live client, and enforce that protocol/gameplay changes target the server plus `client_web`.
- **P2:** Complete native-device verification and add CI checks for Capacitor dependency installation, Android notification declarations, back-button interception, safe-area overlays, and iOS-generated path normalization.
- **P2:** Maintain generated protocol, affix-index, content, and sprite checks as mandatory release gates; pair them with browser exercise and device tests because static type checks cannot detect the known runtime failure classes.
